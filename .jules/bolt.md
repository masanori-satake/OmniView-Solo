## 2026-03-31 - Canvas 2D 変換ループにおける不要な putImageData と clearRect のスキップ
**学び:** WhiteboardProcessor の requestAnimationFrame (60 FPS) ループ内で、変更されていない静的な MedianStacker の ImageData バッファに対して毎フレーム `putImageData()` を呼ぶと、毎秒数GBクラスの不要な CPU→2D Canvas コンテキスト転送が発生していた。また、オーバーレイキャンバスに描画要素がない状態で毎フレーム `clearRect()` を呼び出すのも無駄な描画オーバーヘッドとなっていた。スタックフレームにバージョン番号 (`version`) を導入し、描画キー (`drawStateKey`) を用いたメモ化・状態フラグ制御により、描画が必要なタイミングのみ Canvas 操作を実行することで大幅に CPU/GPU 負荷を削減できた。
**アクション:** 今後 Canvas や Media Stream を扱うリアルタイム処理を追加・変更する際は、毎フレーム描画を愚直に呼び出さず、入力・状態変更時の差分駆動 (Event-driven / Dirty checking) 描画パターンを優先適用する。

## 2026-04-01 - 高解像度画像（1080p）の逆ホモグラフィ変換ループにおける TypedArray 参照キャッシュと行演算・チャンネル展開の最適化
**学び:** `PerspectiveTransformer.getWarpedFrame` はキャプチャ時やホワイトボード画像補間処理時に 1080p（200万画素 = 800万バイト）の ImageData を逆ホモグラフィ変換・バイリニア補間する。200万回の画素ループ内で `imageData.data` や `out.data` のプロパティ参照、行単位で不変な項の重複計算、およびチャンネル (R, G, B, A) ループを実行すると、プロパティルックアップおよびインデックス計算のオーバーヘッドが蓄積していた。プロパティ参照を外側にキャッシュし、行式 (`h7 * y + h8` 等) の抽出と4チャンネルへの代入展開 (unrolling) を行うことで、画素精度（100%一致）を完全に維持したまま 1080p フレームでの変換処理時間を約 13.3%〜27.7%（137.8ms → 119.5ms）削減できた。
**アクション:** 大容量 TypedArray (ImageData) を画素単位で走査する画像処理ループを書く際は、オブジェクトのプロパティアクセスや行レベルで共通な算術式を必ずループ外へキャッシュ・抽出し、短い固定長チャネルループは直接展開することを徹底する。
